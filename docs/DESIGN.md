## 1. 目標

在同一套政策和輸入情境下比較 A／B／C／D 四種調度架構，注入六種故障，量測安全性、可用性與延遲。結論稱為「在指定協議假設下的模型驗證」，不是對實際 BFT 引擎的形式證明。

| 架構 | 做法 | 擋得住 | 擋不住或代價 |
|---|---|---|---|
| A 中央調度加備援 | 一個調度中心，備援中心隨時接手 | 調度中心被炸或斷線 | 被駭時，備援照樣執行錯誤的指令 |
| B 中央調度加在地規則檢查 | 變電所的檢查器拒絕違規指令；斷線時跑事先簽好的輪停表；加上低頻卸載 | 明顯違規的單一指令 | 單看合規、合起來有害的指令；中央失能後只能跑固定備案 |
| C 台電內部 BFT | 台電在自己的 7 個站點各跑一個節點 | 單一站點被駭或被炸；能做全域檢查與動態分配 | 同一管理網域，一次入侵可能打下多個節點；資料全來自台電 |
| D 多組織 BFT | 7 個組織各跑一個節點，f = 2，Q = 5 | 被駭加失聯合計不超過 f 個，一個組織出事只影響一個節點 | 成本和複雜度最高；最弱的組織拉低整體安全；共同輸入資料仍可能是假的 |

## 2. 設計原則（沿用 evsim，改成電網用途）

1. **同一套引擎、同一套政策、同一組情境**：A／B／C／D 只差在決策怎麼送到變電所，結果的差異才能歸因於架構。
2. **政策是純函式、與輸入順序無關**：每個驗證者算出同樣的決策，任何人都能從日誌重算。
3. **真相與可觀察分開**：事件分 `public` 與 `truth`。架構和驗證器只能讀 `public`；故障動作和遺失的訊息只記在 `truth`，給指標用。
4. **指標只從日誌算**：`metrics.py` 不碰架構的內部狀態。
5. **比較一律用配對差（共同亂數）**：網路、負載、故障的亂數都依 key 抽，誠實組和故障組、以及不同架構之間，看到同樣的網路和負載。
6. **只用標準函式庫**：Python 3.10 以上，測試用 unittest。例外是加分項的 Docker 展示：即時模式要真的 Ed25519，需要 cryptography 套件（只裝在容器裡；本機沒有時 8 個即時模式測試會跳過）。
7. **結果可追溯**：每個實驗輸出 CSV 加 meta.json（設定、git commit、已知問題）。

## 3. 協議與故障模型

- 標準 BFT：f = ⌊(n − 1) / 3⌋，Q = ⌊2n / 3⌋ + 1（超過三分之二，和 CometBFT 一致）。n = 7 時 f = 2、Q = 5；n = 4 時 f = 1、Q = 3。`config.py` 由 n 推出 f 和 Q，測試檢查任兩個 Q 至少重疊 f + 1 個節點，而且 f 個節點沉默時仍能提交。
- f 把被駭和失聯的節點合計。活性假設部分同步：每一輪的逾時遞增（`GridConfig.round_timeout(r)`、`vote_timeout(r)`），網路恢復後總有一輪夠長。
- 驗證者集合固定（epoch 不變），動態成員與熱備援列為未來工作。
- 變電所是輕節點：檢查鏈 ID、epoch、高度與序號、饋線與絕對目標狀態、狀態版本、commit proof（至少 Q 個不同驗證者的有效簽章）和區塊頭鏈；TTL 只是次要檢查。拒絕理由的代碼在 `verifier.REJECT_REASONS`，檢查順序見下方「最後一跳與變電所驗證」。
- 保守降級：湊不滿 Q 或沒有新的提交時，變電所維持現狀，只准在地保護性卸載（過載、UFLS）；不自動復閉，也不切換到備案輪停表。A 失去兩個調度中心時也一樣。只有 B 有靜態備案，那是 B 的定義。
- 簽章：標準函式庫沒有 Ed25519，用每個節點一把金鑰的 HMAC 代替（`crypto.py`）。攻破 k 個節點的攻擊者持有 k 把金鑰，只做得出 k 個有效簽章。Docker 展示的即時模式用真的 Ed25519（`gridq/live/keys.py`）。

### 共識的實作（`gridq/consensus/`）

每個驗證者一個狀態機（`tendermint.py`），照 Buchman、Kwon、Milosevic〈The latest gossip on BFT consensus〉（2018）的 Algorithm 1 寫，也就是 CometBFT 跑的協議：提案、prevote、precommit、鎖、valid value、換輪，收到超過 n/3 個驗證者較高輪次的訊息就跳到那一輪。提案者是 `validators[(h + r) mod n]`，沿用 evsim 的輪替。論文假設訊息會 gossip 到送達為止，這裡的網路則會把訊息丟掉，所以有下面幾個建模選擇：

- **計時器對齊**：每一步都由計時器結束。從本輪開始算，提案步在 P = `round_timeout(r)` 結束；prevote 步在「進入 prevote」和 P 較晚的那個之後再過 V = `vote_timeout(r)`；precommit 步在「進入 precommit」和 P + V 較晚的那個之後再過 V。預設 P = 3 + 0.5r 秒、V = 1 + 0.5r 秒。一輪失敗時，每個節點都在本輪開始後剛好 P + 2V 進下一輪，和論文在票全部送達時的時序相同。論文的 prevote、precommit 計時器要收到 Q 票才開始，其餘的票靠 gossip 補；這裡票會遺失，照論文做的話，一張票不見就可能讓一輪永遠卡住。計時器只決定節點什麼時候往下走，不決定投什麼，所以不影響安全。
- **鎖定證明（POL）**：重新提出自己的 valid value 時，提案附上讓它成為 valid value 的 Q 個 prevote 簽章。CometBFT 靠 gossip 傳這些 prevote；少了它們，錯過的節點永遠不能接受這個值，而鎖住的節點又不接受別的值，運氣差的一輪就可能卡死整個高度。
- **區塊本體**：只有收到提案的節點會對那個區塊投 prevote 和 precommit（CometBFT 對沒收到的區塊投 nil precommit）。非 nil 的 precommit 帶著區塊本體，代替 CometBFT 的區塊分片 gossip，所以任何數到 Q 個 precommit 的節點都能提交。
- **追趕**：節點收到已經決定的高度的訊息時，回傳那個高度起的區塊和 commit proof，每個對象、高度、輪次只回一次，代替 CometBFT 的 block sync。對方的票如果正是那個高度提交那一輪、同一個區塊的票，就不回。
- **時槽**：區塊記錄提案時的調度時槽 k，高度 h + 1 在時槽 k + 1 開始時開始；共識拖過了時槽 k + 1 就立刻開始。區塊有效的條件是鏈 ID、epoch、高度、前一個區塊的雜湊和時槽都對（上一個區塊的時槽 < 時槽 ≤ 現在的時槽），而且應用層的 `valid_fn` 接受。`valid_fn` 對同一個區塊在任何時候都要給同樣的答案，否則鎖住的區塊後來變成無效，會讓那個高度卡住；指令過期由變電所驗證器處理。
- **離線節點**：不送也不收訊息，計時器照走。
- **commit proof**：`{height, round, block, sigs}`，`sigs` 是至少 Q 個驗證者對 precommit 摘要的簽章。`messages.verify_commit` 依序檢查鏈 ID、epoch、格式和有效簽章數，拒絕理由是 `wrong_chain`、`wrong_epoch`、`insufficient_quorum`。prevote 簽的是另一個摘要，不能拿來湊 commit proof。
- **雙簽證據**：同一個驗證者在同一輪送出兩個不同的提案或兩張不同的票，記一筆 `EVIDENCE` 事件（每個驗證者、種類、輪次只記一次）。
- **計票**：每個簽過的（驗證者, 值）各算一票。同一個驗證者同一輪投了兩個不同的值（雙簽），兩張票分別算進各自的值，並記一筆證據；CometBFT 在有節點宣稱某個值湊滿多數時，也會保留這種互相衝突的票。早先的版本每個驗證者每輪只算第一張票，exp1 因此找到一個活性問題：鎖定證明裡如果有雙簽者的另一張票，先收到它第一張票的節點只數到不滿 Q 張，拒絕這個證明；誠實節點鎖在不同的區塊上，同一個高度卡了 95 輪（n = 7、2 個雙簽者、遺失率 0.1）。改了之後，不超過 f 個雙簽者時，任何一輪都不會有兩個值同時湊滿 Q，安全不受影響；無故障時結果完全不變（check_consensus、check_island、exp4 的輸出逐位元組相同）。
- **追趕帶出的證據**：追趕收到的 commit proof 裡的 precommit 也當成票處理，所以在另一半、只看過雙簽者一張票的節點，也能記下證據。

理論值也跟著修正。evsim 的 M2 讓沒收到提案的驗證者也能 precommit，Tendermint 和 CometBFT 不會，所以 `theory.round_outcome` 改成只有 prevote 過的驗證者能 precommit；測試裡有一個 n = 4 的反例，照 evsim 的算法會提交，照協議不會。`theory.commit_latency_bound(cfg, k)` 是沒有遺失、前 k 輪的提案者沉默時，第一次提交的最晚時間：前 k 輪各 P + 2V，加上提案、prevote、precommit 三跳的最大延遲。

### 最後一跳與變電所驗證（`gridq/verifier.py`、`gridq/lasthop.py`）

信任邊界在最後一跳：變電所只執行自己驗得過的指令。中間轉送的人（被駭的調度中心、轉送站、線路上的人）可以延遲或丟掉指令，但不能偽造、調換順序或重放。

- **變電所記住的狀態**：信任的最新區塊頭（高度和雜湊，從創世區塊開始）、最後執行的指令序號、狀態版本（每執行一道指令或做一個在地動作就加一：UFLS 跳脫、孤島崩潰、B 的輪停表）、各饋線狀態，以及政策要用的記帳：每條饋線上次切換的時間、累計停電時間（每次停電結束時以整分鐘記入，`verifier.outage_s`）和上一次停電的長度。
- **指令**：一律是絕對狀態（「F3 設為關」），不用切換。欄位是變電所、饋線、目標（on／off）、序號（每座變電所各自遞增）、決策依據的狀態版本和到期時間（決策時槽的開始時間加 `command_ttl_s`）。C、D 的指令放在區塊裡，由區塊綁到鏈、epoch 和高度，再由 commit proof 認證。A、B 由調度中心逐道簽章（`verifier.sign_command`），之後的指令檢查相同。
- **檢查順序**，第一個不過的就是記下的拒絕理由：
  1. 鏈 ID 與 epoch（`wrong_chain`、`wrong_epoch`）。只數簽名、不檢查鏈 ID 的閘道，會接受另一條用同一組驗證者金鑰簽的鏈（例如演練鏈）上的區塊。
  2. 區塊高度不高於信任的區塊頭（`stale_seq`）。和信任區塊頭相同的副本直接丟掉、不記事件，因為每個驗證者都會送一份。
  3. commit proof（`insufficient_quorum`；A、B 是調度中心的簽章，`bad_signature`）。這一項永遠開著。
  4. 高度超前一格以上的有效區塊先暫存，等缺的高度補齊。下一個區塊要接在信任的區塊頭後面（`header_mismatch`，用 `chain.verify_chain(prev=…)`）。
  5. 逐道檢查發給自己的指令：饋線存在（`unknown_feeder`）、目標是絕對狀態（`relative_target`）、序號大於最後執行的（`stale_seq`）、狀態版本等於目前版本（`state_mismatch`）、以本地時鐘還沒過期（`expired`）、B 的在地規則（`policy_violation`）。
- **送達**：每個提交了區塊的驗證者都把區塊和 commit proof 送給每座變電所。f 個驗證者扣住不送時，一個誠實驗證者的副本就夠。變電所缺高度時向所有驗證者要，5 秒後還缺就再要一次，間隔加倍到 60 秒。
- **狀態回報上鏈**：變電所用自己的金鑰簽署狀態（版本、最後執行的序號、各饋線狀態和上面的記帳），在狀態改變後 0.5 秒和每個調度週期各送一次給所有驗證者（A、B 則送給兩個調度中心）。提案者把每座變電所最新的回報放進區塊；指令由區塊裡的回報（C、D 還有時槽的量測）算出，每個驗證者都會重算一次，和提案不同就不投票（`lasthop.ChainDispatch.valid`：C、D 用 `PolicyDispatch`，exp4 和測試用不看電力狀態的 `RotatingDispatch`）。所以漏收或拒絕了指令的變電所，或保護動作跳脫了饋線的變電所，下一個時槽會收到依它真正狀態算出的指令，不會一直對不上版本。
- **報告必收規則**（`report_inclusion_s`，預設 60 秒）：提案者可以把新的狀態回報留在區塊外，區塊照樣有效，只是依舊的狀態算指令，所以被攻破的提案者可以藉此拖住輪停。誠實驗證者只在一種情況對新的提案投 nil prevote：區塊漏掉了一份自己已經收到 60 秒以上、比鏈上新的回報。規則只管 prevote，鎖住的區塊照常 precommit，所以不影響安全。exp1 顯示，沒有這條規則時 2 個雙簽者讓 73% 的分歧輪次提交了舊狀態的區塊，打擊後每次多 5.5 次 UFLS；有規則時一個也沒有。代價：驗證者之間不轉傳回報，停擺後回來的驗證者要等每座變電所下一次回報（最多一個調度週期），在那之前它的提案會被拒絕（exp2，§6）。
- **時鐘**：TTL 用變電所自己的時鐘。時鐘慢，舊指令看起來還沒過期；時鐘快，新指令一到就過期。exp4 裡時鐘快 1 小時的完整驗證器一道合法指令都沒執行，整段期間該停電的饋線全部照常供電。所以重放要靠序號和狀態版本擋，TTL 只是第二道防線；時鐘被干擾時，TTL 反而會擋掉合法的卸載指令。

### 電力模型（`gridq/power.py`、`gridq/loads.py`）

這是分散式系統的專題，電力只做到能呈現「固定備案在供電低於假設時超載，依當下狀態重算能避開」（問題 22）：不做潮流和保護暫態，保護電驛照現在的方式在地動作。

- **孤島**（`loads.default_island`）：4 座變電所各 3 條饋線，共 12 條。調度能切的最小單位是饋線（問題 21），所以每座變電所有一條關鍵饋線，帶著醫院、加壓站、基地台或避難所，也帶著同一條線上的住宅；其餘是住宅或商業饋線。饋線的權重取上面最重要的負載：醫院 100、加壓站 90、基地台 80、避難所 70、住宅 2、商業 1。孤島尖峰需求約 38 MW，四條關鍵饋線合計的尖峰約佔 21%。
- **負載**（`loads.Loads`）：每種負載一條 24 小時的日曲線乘上尖峰值，再乘上 1 加雜訊（每條饋線每分鐘一個 AR(1)，相對標準差 3%，亂數依種子、執行和饋線抽）。決策者只看沒有雜訊的公開預測。曲線和尖峰值是示意值，不是量測資料（醫院、加壓站、基地台的資料缺口見專題文件）。
- **供電 G(t)**（`power.Supply`、`GridConfig.supply_profile`）：孤島裡還能用的發電量，以尖峰需求的比例給，點與點之間線性變化，同一時間兩個點代表線路被切斷的瞬間變化。預設一開始 70%，凌晨 3 點左右被打擊降到 45%，14 點到 20 點慢慢恢復到 60%；每次執行把 0 點以後的各點一起平移一個 ±1 小時內的亂數。
- **冷載**（`power.cold_factor`）：停電 d 秒後復電的饋線，負載乘上 1 + (M − 1) × min(1, d / D)，在 D 秒內線性降回 1；M = 2、D = 1800 秒。政策用同一個公式規劃。
- **平衡與 UFLS**：每次切換、供電變化和每 60 秒檢查一次。負載超過 G(t) × 1.05 持續 2 秒，簡化的低頻卸載（UFLS）依固定順序整段跳脫（第 1 段先，關鍵饋線不參與），直到負載不超過 G(t)。UFLS 不知道政府的規則，可能切掉輪停剛復電的饋線。
- **崩潰**：所有段都切了還不夠，孤島全黑：所有饋線斷開，1 小時內什麼都合不上（`dead_bus`），之後供電回來，要由調度重新復電，而且有冷載。
- **在地動作**：UFLS 跳脫、崩潰和 B 的輪停表都是變電所的在地動作（`Verifier.local_action`），狀態版本加一，之前算好的指令會以 `state_mismatch` 被拒絕，下一個時槽依新狀態重算。
- **量測**（`Island.measure(k)`）：時槽 k 開始時讀到的供電（全黑時為 0）和各饋線在這個時槽的預測負載，取到 0.1 kW。四種架構的決策者拿到同一份；C、D 的區塊帶著量測，驗證者檢查和自己讀到的相同。

### 分配政策（`gridq/policy.py`）

一個純函式 `decide`，A、B 的調度中心、C、D 的委員會和 B 的預簽輪停表都呼叫它，輸入也相同：每座變電所最新的簽署回報，和時槽的量測。

- **預算**：供電 × (1 − 5%)。每條饋線的負載是預測乘上冷載倍率，正要復電的饋線也算進冷載。
- **順序**：（1）關鍵饋線依權重（醫院、加壓站、基地台、避難所），再依累計停電時間，放得下就供電；（2）復電不到 30 分鐘（`min_dwell_s`）的非關鍵饋線，放得下就繼續供電，避免反覆切換；（3）其餘非關鍵饋線依急迫度（權重 × 累計停電時間）由大到小，放得下就供電，這就是輪停：停電越久越急，供電時就不再增加；（4）停電不到 30 分鐘的放最後。規劃負載永遠不超過預算。
- **時間以整分鐘比較**：政策裡的時間長度取整分鐘（`TIME_STEP_S`），變電所也以整分鐘記帳，所以晚幾秒到的指令不會改變兩條饋線的先後，相同的依名稱排序。委員會比調度中心多花幾百毫秒，提案者離線時多一輪要幾秒，各變電所收到的時間也不同；不取整的話，這幾秒就會讓四種架構的輪停順序分岔。取整後，無故障時四種架構做出完全相同的決策，C、D 少了不超過 f 個驗證者時也和無故障時完全相同（§7 第 3 步）。
- **指令**（`commands_for`）：和回報不同的絕對目標，依變電所、饋線排序，從變電所最後執行的序號往下編，附上假設的狀態版本；到期時間是時槽開始加 `command_ttl_s`。
- **兩種檢查**（exp5 會用）：`check_local` 是 B 的變電所看得到的單一指令：不准切關鍵饋線，每座變電所每個調度週期最多切換 2 次（`LocalEnforcer`）。`check_global` 是 C、D 驗證者看得到的整組指令：對照孤島狀態和供電，規劃負載超過預算，或放得下卻讓關鍵饋線停電，就拒絕。C、D 的驗證者更進一步，只接受和自己算出的 `decide` 完全相同的指令（`PolicyDispatch`）。
- **B 的預簽輪停表**（`static_table`）：事先用預測和固定的供電（尖峰需求的 40%，`plan_supply_share`）跑 `decide`，每座變電所拿到自己的那幾列。

### 四種架構的決策路徑（`gridq/central.py`、`gridq/lasthop.py`、`gridq/substation.py`、`gridq/arch/`）

`sim.Simulator` 擁有時間、日誌和孤島，`arch.get(cfg.arch)` 建立決策路徑，故障掛勾收到的 `sim` 就是這條路徑。四種架構共用同一組負載、供電、網路亂數和故障物件，差別只在決策怎麼送到變電所。變電所那一端（驗證器、收區塊或批次、B 的備案、簽署回報）在 `substation.py`，四種架構共用。

- **A**（`central.CentralPath`）：調度中心 `centre` 和備援 `backup` 各有金鑰，變電所兩個簽章都接受。值班的中心每 30 秒送心跳給另一個；備援 90 秒沒收到就以下一個任期接手（`FAILOVER`），中心恢復後以備援身分回來。被切斷但還在跑的中心會繼續調度，所以分區時兩個中心可能同時值班（split brain），變電所執行符合自己狀態版本的那一份，其餘拒絕。每個時槽開始，值班的中心用每座變電所最新的回報和時槽的量測跑 `decide`，把簽好的指令和一個簽好的「仍在調度」記號一起送給每座變電所。兩個中心都失去時，變電所維持現狀（問題 26）。
- **B**：同 A，加上每座變電所的在地檢查（`LocalEnforcer`）和預簽輪停表：900 秒沒收到任何中心的「仍在調度」記號，變電所就在每個時槽開始依表做在地動作，再聽到中心就停。
- **C**：台電 7 個站點的委員會（`lasthop.LastHop` 加 `PolicyDispatch`）。提案者把每座變電所最新的回報和時槽的量測放進區塊，指令由這兩者算出，每個驗證者重算，不同就不投票；變電所驗 commit proof（見上方「最後一跳」）。
- **D**：和 C 相同的程式，7 個驗證者屬於 7 個組織（`orgs`），exp6 的共因模型會用到。
- **失去站點**（`faults.Offline`）：一個故障物件套到四種架構，每個節點名稱在有它的架構裡生效：`centre`、`backup`（A、B）、`v0` 到 `v6`（C、D）或變電所。離線的節點不送也不收，計時器照走，時段結束就恢復。

### 故障注入（`gridq/faults.py`）

同一個故障物件套到四種架構，每種架構只呼叫自己有的掛勾，其餘維持誠實（沿用 evsim 的寫法）。網路分區、延遲和斷線干擾是網路設定（`network.py`），不是故障物件。

| 故障 | 做什麼 | 掛勾 | 實驗 |
|---|---|---|---|
| `Offline` | 節點不送也不收，時段結束就恢復 | `node_up` | exp2、exp6 的癱瘓 |
| `Equivocate` | 被攻破的提案者對兩半的驗證者送不同的區塊，被攻破的驗證者在那一輪對兩半投不同的票。誠實驗證者每輪隨機對分，被攻破的都在第一半，這是攻擊者最有利的分法。孤島上的第二個區塊是漏掉新狀態回報的那一個，也是誠實驗證者唯一會接受的另一個區塊 | `proposal`、`vote` | exp1 |
| `Replay` | 最後一跳錄下送達的訊息，之後再送 | `last_hop` | exp4 |
| `HackedCentre` | 攻擊者控制調度中心送出的指令，用中心自己的金鑰簽；心跳和「仍在調度」記號照常送 | `central_commands` | exp5、exp6（A、B） |
| `CompromisedValidators` | 攻擊者握有 b 個驗證者的金鑰：提案夾帶攻擊指令；每個時槽開始時用手上的金鑰簽一份提交證明，直接送到每座變電所。不滿 Q 把金鑰時簽名不夠，滿 Q 把時變電所接受，之後只跟攻擊者的鏈。其餘照協議走 | `proposal`、`last_hop`，`inject` 送偽造的區塊 | exp5、exp6（C、D） |
| `Observe` | 不改變行為，只記錄每個節點收到哪些變電所的狀態、指令和全島量測 | `proposal`、`last_hop`、`central_commands` | exp6 |

攻擊指令（`attack_targets`）有四種：`restore_all` 全部饋線復電（每道單看都合規，合起來遠超過供電）；`cut_critical` 照政策但切掉所有關鍵饋線（明顯違規）；`starve` 照政策但讓 S4 的非關鍵饋線一直停電（每道合規，輪停不公平）；`freeze` 不送任何指令（調度看起來還活著，輪停卻停了）。

### 共因模型（`gridq/theory.py`、`gridq/metrics.py`）

問題 19 的模型。每個節點各自以自己的機率被攻破（某個站點被入侵、弱組織被入侵）；另外有幾個彼此獨立的共同事件，一發生就同時拿下它涵蓋的全部節點：同一個組織的帳號、人員和網路（C 的 7 個節點和 A、B 的 2 個中心都在台電），以及同一套軟體的零時差漏洞（每個節點都跑）。

- `theory.compromise_prob_events` 對共同事件的所有組合求和，精確算出至少 k 個節點被攻破的機率；`theory.sample_compromised` 依同一個模型抽樣，給 exp6 的蒙地卡羅檢查用。
- `metrics.break_difficulty` 從一次執行日誌裡的節點與組織對照（`run_meta["arch"]["orgs"]`）建立模型，算出讀取、癱瘓、偽造三個門檻各自的機率；門檻由 exp6 量測（C、D 是 1、f + 1、Q，A、B 都是 1）。
- `theory.break_even_weak_risk` 找出 D 和 C 一樣容易被攻破 k 個節點時，弱組織節點的風險，也就是分界圖上的線。
- 機率全是假設，模型只顯示趨勢，不是真實的機率。

| 實驗 | 注入 | 要驗證 | 主要模組 |

## 6. 刻意的簡化（之後可改）

- 分區期間跨群組的訊息直接丟掉，不排隊，靠協議在後面的輪次重送。
- 共識訊息不重送：一則訊息遺失就是遺失，靠下一輪重來，這也是 `round_success_prob` 的假設。CometBFT 會 gossip 到送達為止，所以遺失率高時這裡的提交延遲比實際引擎悲觀（n = 7、p = 0.3 時第一次提交的 p95 約 800 秒）。少了 f 個驗證者時剩下的 Q 個一則都不能掉：遺失率 0.1、不重送時，停擺期間只有 44% 的時槽決定；每則重送 2 次就回到 100%（exp2）。
- 投票只送一次、不 gossip：雙簽者只有在某個誠實節點看到它的兩張票時才被抓到，實際上是 commit proof 經由追趕送到另一半的時候；一輪兩半都湊不滿 Q 時沒有人看到（exp1 的 `caught` 欄）。
- 驗證者之間不轉傳狀態回報（CometBFT 的 mempool 會在重新連上時補）：停擺後回來的驗證者要等變電所下一次回報，在那之前它的提案被報告必收規則拒絕，C 在兩小時停擺後最多約 400 秒才恢復（exp2）。
- 遺失和分區在送出時判定；分區開始前送出的訊息照常送達。
- 斷線模型以節點為單位：任一端斷線，訊息就遺失。
- 簽章是對稱式 HMAC，驗證端持有所有金鑰，只模擬「沒有金鑰就簽不出來」。Docker 展示的即時模式改用 Ed25519，每個節點只有自己的私鑰，變電所只有公鑰（§7 第 5 步）。
- 最後一跳的攻擊者只會把錄下的整則訊息（區塊加 commit proof）再送一次。扣住訊息、晚一點才放的攻擊沒有模擬；那只有 TTL 擋得住，而且時鐘要準。
- 驗證者送給變電所的區塊和變電所的狀態回報都不重送：區塊遺失靠其他驗證者的副本和補洞，回報遺失靠下一次狀態改變或週期回報。
- 變電所的時鐘偏差整次執行固定，不模擬漂移或被干擾的過程。
- 電力物理只抽象成可供電上限 G(t)、饋線負載與權重、冷載倍率、超載時的簡化 UFLS；不做潮流與保護暫態。
- UFLS 一段一段切到負載不超過 G(t) 為止，沒有它能挽回的失衡上限，所以超載通常以 UFLS 收場，只有關鍵饋線本身就超過 G(t) 時才崩潰（UFLS 不切關鍵饋線）。實際的 UFLS 只設計來處理一定比例的失衡（大約 25% 到 50%），超過就可能直接全黑，所以這裡對 B 的備案偏寬容。
- 所有決策者看到同一份量測：時槽開始的供電讀數和公開的負載預測。量測本身被竄改（共同輸入資料是假的）不在這一步的範圍。
- 政策知道真正的冷載公式，以整條饋線計；負載曲線、孤島和供電情境都是示意值。
- 政策為了不觸發 UFLS 和公平輪停，用電比較保守（5% 備轉、整條饋線、每條復電的饋線都算冷載、最短停留 30 分鐘），打擊後只用到 G(t) 的約七到八成；維持現狀或固定輪停表加上 UFLS 可能多供一些電（§7 第 3 步）。這是四種架構共用的政策選擇，之後可以把這些參數拿來掃描。
- B 的變電所依輪停表合上被 UFLS 跳脫的饋線；鎖住跳脫饋線的做法會少跳一些，也少供一些電。
- A 失去兩個調度中心後，孤島崩潰了也沒有人復電：黑啟動後孤島有電，但所有饋線維持斷開。
- A、B 的心跳不簽章；被切斷的中心不知道自己被切斷，會和接手的備援同時調度。
- 時間長度以整分鐘比較、整分鐘記帳，讓幾秒的執行延遲差異不改變輪停順序（§3「分配政策」）。
- 被攻破的驗證者在 exp5 只做提案夾帶和偽造提交證明，其餘照協議走；exp6 的癱瘓以停止投票模擬（等同離線）。被駭的 A、B 調度中心照常送心跳和「仍在調度」記號，所以不送指令（`freeze`）時備援和輪停表都不接手。
- 共因模型的事件彼此獨立：同時針對多個弱組織的攻擊、組織之間共用的供應商或人員都會提高 D 的風險，沒有模擬。
- C、D 的變電所收到整個區塊（commit proof 簽的是整個區塊），所以看得到全島的狀態和指令；在區塊頭放指令的 Merkle root、每座變電所只收自己的指令加證明，是未來工作（exp6）。

**政策的用電代價**：政策為了不觸發 UFLS 和公平輪停，用電比較保守：預算留 5% 備轉，以整條饋線計，每條復電的饋線都算冷載。打擊後供電 50% 時，C、D 滿足的用戶需求平均只有 G(t) 的約 70%，加上冷載約 83%。A 維持現狀、B 的表加上 UFLS，都把負載塞到接近 G(t)，輪停少，冷載也少，所以能多供一些電：A 在 35% 以上，B 在 25% 到 35%。代價是誰停電由電驛的段數決定，A 還讓同一批饋線整天停電（公平性 0.62 到 0.74）。這是四種架構共用的政策選擇，不是決策路徑的差別，無故障時四種架構的用電滿足率完全相同。備轉比例、最短停留時間和饋線分段之後可以拿來掃描。

完整數字（95% 信賴區間、每種拒絕理由、換手與備案次數）在 `results/main/check_island.csv`，已知問題在同名的 `.meta.json`，圖在 `.svg`（情境）和 `_sweep.svg`（敏感度）。重跑：`python3 experiments/check_island.py`（4 核約 2 分鐘）。

### 第 4 步的結果

**exp1 作惡節點**（`experiments/exp1_equivocation.py`）。共識部分：n = 4 和 7，b 個被攻破的驗證者雙重簽名（§3「故障注入」的 `Equivocate`），每格 20 次 × 50 個高度。下表是訊息不遺失的結果，遺失率 0.1 的結論相同：

| n | 雙簽者 b | 衝突提交 | 有衝突的執行 | 誠實節點沒提交的高度 | 雙簽者被抓到 |
|---|---|---|---|---|---|
| 4 | 1（f） | 0 | 0／20 | 0 | 100% |
| 4 | 2（f + 1） | 每次 1 個高度 | 20／20 | 96% | 0% |
| 7 | 1 | 0 | 0／20 | 0 | 0% |
| 7 | 2（f） | 0 | 0／20 | 0 | 100% |
| 7 | 3（f + 1） | 每次 1 個高度 | 20／20 | 92% | 5% |

- 不超過 f 時沒有衝突提交，每個誠實驗證者都提交每個高度。代價是被對分的輪次失敗：n = 7、b = 2 時提交延遲的 p95 從 0.23 秒變成 4.1 秒，多一輪。
- f + 1 個雙簽者每次都讓一個高度的兩個區塊都被提交。兩份 commit proof 是同一輪的，至少共用 f + 1 個簽名者，而且全是被攻破的，所以可以追責。分叉之後，攻擊者沒跟的那一半永遠湊不滿 Q（誠實節點沒提交的高度 92% 到 96%），這是超過 f 之後預期的活性損失。
- n = 7、b = 1 時兩半都湊不滿 Q，沒有任何節點同時看到雙簽者的兩張票，所以抓不到（§6：投票不 gossip）。
- 這個實驗找到並修好計票的活性問題（§3「共識的實作」的「計票」）。

孤島部分（C，24 小時，5 個種子 × 4 次）：被攻破的提案者送出的第二個區塊，是漏掉新狀態回報的那一個。

|---|---|---|---|---|
| 有 | 1 | 0 | 11 | 0 |
| 有 | 2（f） | 0 | 36 | 0 |
| 沒有 | 2（f） | 分歧輪次的 73%（702 個區塊） | 0 | 5.5 |
| 沒有 | 3（f + 1） | 214 個區塊，20 次執行都分叉 | 134 | 3.4（可用率 81%） |

- 沒有規則時，2 個雙簽者就讓 73% 的分歧輪次提交了舊狀態的區塊：沒有衝突，安全還在，但決策品質被拖累，打擊後每次多 5.5 次 UFLS。

**exp2 節點離線**（`experiments/exp2_offline.py`）。共識部分：36 個五分鐘的時槽，k 個驗證者在第 6 到 18 個時槽（一小時）離線，離線的都是接下來會輪到的提案者（延遲的最壞情況）；訊息不遺失、遺失率 0.1，以及遺失率 0.1 加每則重送 2 次，每格 20 次。

### 第 5 步：Docker 展示

`gridq/live/` 把模擬器的共識、派工規則和變電所驗證搬到真的網路上：每個節點一個行程，用真實時鐘、UDP 和 Ed25519。`demo/` 用 Docker 跑 7 個驗證節點（v0 到 v6）、4 個變電所（S1 到 S4）和一個監看程式（儀表板在 <http://localhost:8080>），另有產生金鑰和攻擊者兩個工具容器。`python3 demo/scenario.py` 依序跑 8 個情境並逐項檢查。

**直接用模擬器的程式，不是重寫**：`consensus.Committee`／`Validator`（提案、prevote、precommit、鎖、換輪、追趕、雙簽證據）、`lasthop.RotatingDispatch`（每個時槽輪停一組饋線，指令由鏈上的變電所狀態回報算出，每個驗證者重算檢查，也照樣執行報告必收規則）、`substation.Substation` 與 `verifier.Verifier`（變電所的全部檢查、補洞、簽署的狀態回報）、`faults.Equivocate`（雙簽）。

**即時模式另外加的東西，和原因**：
- 金鑰（`keys.py`）：Ed25519，介面和 `crypto.KeyRing` 相同。每個容器只掛載自己的私鑰和所有人的公鑰；驗證者和變電所的公鑰分成兩組，變電所的簽章不會算進 Q。偽造 commit proof 真的得偷到 Q 把私鑰。
- 一個行程一個驗證者（`validator.LiveCommittee`）：繼承 `Committee`，只啟動本地的驗證者，訊息走 UDP（給自己的直接排入），沒有時槽上限，追趕回覆切成一個封包放得下的大小。
- 簽章守門員：把簽過的最新（高度、回合、步驟）寫進檔案，`docker compose stop`／`start` 之後不會在同一處再簽一次（CometBFT 的 priv_validator_state）。
- 追趕請求：重啟的驗證者躲在守門員後面不出聲，別人就不會回它，所以它在啟動時、以及聽到領先兩個高度以上的訊息時，主動向其他驗證者要錯過的區塊。
- 轉傳提案：每個驗證者把收到的每個簽過的提案轉給其他驗證者一次，代替 CometBFT 的 gossip。雙簽者分給兩半的兩個區塊因此大家都看得到，雙簽者就被抓到；模擬器不轉傳，exp1 一輪兩半都湊不滿 Q 時沒有人看到（§6）。
- 只把目前或上一個時槽的區塊送到變電所：追趕中的驗證者不重送舊區塊，變電所缺的高度自己會要。
- 時間（`runtime.live_config`）：所有容器共用起點 `GRIDQ_T0`，時槽 8 秒，第 0 回合等提案 2 秒、每個投票步驟 1 秒、每回合加 0.5 秒；指令有效 3 個時槽，報告必收規則用半個時槽。
- 網路名稱：容器靠 Docker 的 DNS 找彼此，背景執行緒每秒解析一次，停掉的節點不會卡住主迴圈。分區用 `docker network disconnect`，接回時要帶 `--alias` 把服務名稱還給它（`scenario.py` 已處理）。

**8 個情境的結果**（`python3 demo/scenario.py`，在雲端的 Docker 上 26 項檢查全部通過；時間是最後一次執行的數字，每次會差一兩秒）：

| 情境 | 做法 | 結果 |
|---|---|---|
| 1 正常運作 | 7 個驗證者 | 每個時槽在第 0 回合提交（24 秒內 3 個區塊）；4 個變電所驗過 Q 個簽章才執行，每個時槽各切換 2 條饋線 |
| 2 停 2 個 | `docker compose stop v5 v6` | 剩 5 個 = Q，照常出塊（24 秒內 3 個區塊），變電所照常跟上 |
| 3 再停 1 個 | `docker compose stop v4` | 剩 4 個 < Q，32 秒內一個區塊都沒有，4 個驗證者一直換輪；變電所停在同一個區塊，饋線狀態不變 |
| 4 重啟 | `docker compose start v4 v5 v6` | 8 秒內 7 個都跟上同一高度、恢復出塊，沒有衝突 |
| 5 分區 4｜3 | `docker network disconnect` v4、v5、v6 | 兩邊都不出塊；接回後 11 秒恢復，沒有衝突 |
| 6 雙簽 | v3 改成 `Equivocate` | 其餘 6 個驗證者都舉證 v3 雙簽，沒有衝突提交，照常出塊 |
| 7 最後一跳攻擊 | 攻擊者直接把區塊送到變電所 | 重放舊區塊 → `stale_seq`；真的 commit proof 配上改過的區塊 → `insufficient_quorum`；只有 2 把金鑰的偽造 → `insufficient_quorum`；別條鏈 → `wrong_chain`。變電所仍只跟委員會的鏈 |
| 8 共因 | 攻擊者拿到 v2 到 v6 的 5 把金鑰 | 偽造的區塊有效，4 個變電所都執行（全部停電），之後委員會的區塊反而被拒絕（同一高度的是 `stale_seq`，再下一個高度接不上攻擊者的區塊，是 `header_mismatch`）。這就是 Q 的安全邊界：C 的 7 個站同屬台電，一次入侵可能同時拿到 5 把；D 要同時攻破 5 個不同組織 |

**測試**：`tests/test_live.py` 8 項，沒有 cryptography 時跳過。金鑰只能由持有者簽、私鑰要對得上公鑰、產生的私鑰檔權限 600；守門員重啟後不重簽；在單一行程裡跑整個孤島（`live/cluster.py`，每個節點一個執行緒和 UDP 埠，時槽 0.6 秒）：正常出塊而且狀態回報上鏈、停 2 個仍出塊而停 3 個不出塊且變電所不動、雙簽者被抓且沒有衝突、最後一跳的四種攻擊都被拒絕。

**展示的限制**：
- 派工規則是輪停（`RotatingDispatch`），沒有電力模型；電力和政策的結果看 check_island 和 exp5。
- 容器在同一台機器上：看不到延遲、遺失和時鐘偏差（這些看 exp3、exp4）。分區是真的斷網，延遲沒有模擬。
- 變電所的狀態只在記憶體裡，重啟變電所容器會從創世區塊重來；展示時不要重啟變電所。
- 攻擊者從驗證者的 `/chain` 讀區塊，代替從線路上錄下傳送內容；它讀變電所的 `/status`，代替竊聽狀態回報。
- 只示範一個雙簽者；兩個以上要在行程之間協調，展示沒有做（exp1 有）。
- 攻擊者拿到 Q 把金鑰之後要換一組驗證者（epoch 變更）才能恢復，沒有實作；情境 8 之後要重新開始。

重跑：`python3 demo/scenario.py`（約 8 分鐘，需要 Docker）；沒有 Docker 時 `python3 -m gridq.live.cluster` 在單一行程裡跑同樣的節點。
